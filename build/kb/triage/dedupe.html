Triage: duplicate reports

owner support desk accepted reviewed 2026-10-29 · 0 days ago

A busy morning brings hundreds of reports about the same thing. We keep one ticket per issue and merge every duplicate into it, so engineering sees one thread with a count.

The rule

A report is a duplicate only when the evidence supports the same cause, under decision 0002, which replaces subject-only matching.

  1. Read the body and look up the tenant locale, booking-form version, and report channel.
  2. Confirm the mechanism: day-first app/email or booking-v2 parser swaps go to the parser ticket; booking-v3 hint/reader disagreement goes to the hint ticket.
  3. Merge only when evidence agrees with that cause. Search by subject, but never decide by subject alone. Count each report ID once.
The same subject can describe different bugs. Different subjects can describe the same bug. Tenant data determines the classifier's route; browser locale and intake tags can be wrong.

When you are unsure

Keep the report separate and request the missing input, booking ID, timezone and timestamps. One-day and timing anomalies need investigation even when the classifier returns parser. Do not merge unknown tenants on subject alone. See the signed decision’s unresolved-report checklist.
